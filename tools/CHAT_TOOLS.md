## §2 Конектор «Lens GitHub» — 7 інструментів

| Інструмент | Для чого |
|---|---|
| `gh_read` | прочитати файл; великі — діапазоном рядків `start_line`/`end_line` |
| `gh_list` | тека або все дерево репо (`recursive`) |
| `gh_log` | останні коміти гілки |
| `gh_commit` | **один коміт з багатьох змін**: `edits` (заміна фрагмента, `old` рівно 1 раз) · `content` (новий файл) · `content_base64` (бінарний) · `blob` (файл, завантажений квитком `put`) · `from`+`move` (перенести) · `delete`; `dry_run` показує точний розмір |
| `gh_ticket` | квиток на 10 хв для контейнера: `tar` (усе репо) · `get` (один файл) · `put` (файли → blob-и для `gh_commit`) — §2-б |
| `gh_branch` | гілки: список · створити · видалити |
| `gh_actions` | workflow: список · прогони · кроки · лог · запуск · перезапуск · скасування |

## §2-б Квиток: файли повз контекст

**Коли.** Файл великий (≳ 20 КБ) або бінарний (xlsx, png, pdf); треба все репо в контейнер (лінт, валідатор, греп); файли з репо A в репо B.
Дрібні текстові правки — як і раніше, `gh_read` + `gh_commit {edits}`.

**Як.** `gh_ticket` повертає `URL=…` і готовий рядок для контейнера. `note` — коротко «навіщо» (іде в лог Cloudflare). Квиток діє 10 хв, одна операція, один репо; `put` — на всю пачку файлів у межах цих 10 хв.

Рецепти (дослівно зі `tools/lens-gh/smoke.sh`; змінні `URL`, `DIR`, `FILE` задаєш перед рядком):

**усе репо в теку** — квиток `op: tar`:
```
mkdir -p "$DIR" && curl --fail -sS "$URL" | tar xz --strip-components=1 -C "$DIR"
```

**один файл + звірка sha** — квиток `op: get`, `path`:
```
curl --fail -sS "$URL" -o "$FILE" && git hash-object "$FILE"
```

**файл → blob (на кожен файл пачки)** — квиток `op: put`:
```
{ printf '{"content":"'; base64 -w0 "$FILE"; printf '","encoding":"base64"}'; } | curl --fail-with-body -sS -X POST -H 'Content-Type: application/json' --data-binary @- "$URL"
```

Після `put` → `gh_commit {changes: [{path, blob: "<sha>"}]}` — спершу `dry_run` (покаже `path · sha · розмір`), потім «так».

**Пастки, які рецепти вже обходять** (не «спрощувати»):
- `curl` без `--fail` на помилці мовчки збереже сторінку помилки під іменем `.xlsx` → завжди `--fail` + звірка `git hash-object` з sha, який назвав квиток `get` або відповідь `put`.
- tarball GitHub кладе все в теку `Konst-Andre-<репо>-<sha>/` → `--strip-components=1`.
- base64 з переносами рядків ламає JSON для `put` → `base64 -w0`.

**Що квиток НЕ дає.** `tar` — знімок файлів без `.git`: історії й `git log` нема (для них — `gh_log`). Квиток закріплений на коміт у момент видачі: гілка зрушила — видай новий.

**Безпека.** URL квитка — доступ на 10 хв; не класти в документи, самері, репо (у логах Cloudflare він сам ховається як `REDACTED`). Ключ до GitHub із воркера не виходить.

**Межі.** Окремого ліміту на квитки нема. Cloudflare Free — 100 000 запитів на добу на акаунт (квиток ≈ 2); GitHub — 5 000 запитів на годину на токен (квиток ≈ 1–3). Розмір `put` — до 50 МБ на файл.

## §3 Правила запису (для будь-якого Project)

1. **Спершу дивлюсь, потім пишу.** `gh_log` → голова гілки; читаю файли, які правлю.
2. **`dry_run` → план показано Konst → «так» → `gh_commit` з `expected_head`** (sha голови, яку я бачив). Без `expected_head` конектор запис у наявну гілку відхиляє; зрушила гілка — перечитати й повторити.
3. **Один хід = один коміт** (може містити багато файлів). Правки — фрагментами (`edits`), не цілими файлами: дешевше й безпечніше.
4. **Після коміту — read-back:** перечитати записане й звірити.
5. **Гілки.** Працюємо в `main`, окремі гілки не заводимо без причини. Видалити гілку — лише на пряме слово Konst і після звірки, що в ній нема нічого, чого нема в `main`. `main` конектор не видалить ніколи.
6. **Токени й ключі — ніколи в тексті:** ні у файлах, ні в самері, ні в памʼяті, ні в репо (репо публічні). Токен GitHub живе в секреті воркера, тому в інструкції Project він не потрібен — **клон репо в контейнер тепер квитком `tar` (§2-б)**, не `git clone` з токеном. Засвітився в чаті — сказати Konst: секрет під заміну.
8. **Текст для ручної вставки видається в чат цілком.** Інструкція Project, промпт, значення для дашборду — агент дає в тому ж ході повним текстом у code block, готовим до копіювання. «Лежить у репо / у файлі» видачу не замінює: Konst працює з телефона.
9. **Ручні дії Konst — агент нагадує сам.** Наперед: окремий блок «Від тебе» — що, де, коли (увімкнути/вимкнути конектор, секрет у дашборді, вставити інструкцію). Після підтвердження — ✅ з датою в самері (§0), щоб наступний чат не просив повторно. Не певен, чи вже зроблено, — спитати один раз, не пропонувати знову.
7. **Великі й бінарні файли — квитком** (`put` → `gh_commit {blob}`), не через `content_base64`: так файл не проходить через контекст, а sha звіряється з `git hash-object`.

## §4 Документи Project

- Агент **сам**, без нагадування, створює, замінює й видаляє доки свого Project.
- Роль Project: **незмінне** (що рідко змінюється) + **транспорт** (файл чекає, поки отримає дім у репо).
- Порядок транспорту: коміт у репо → read-back ≡ → **лише тоді** видалити з Project. У Project нема історії: видалене — назавжди.
- Кожна зміна доків Project скидає кеш усім чатам цього Project — писати пачкою, не чернетками.
- **Естафета самері між чатами.** Закриття сесії: самері → репо (дім) + та сама копія → Project (транспорт), у стартовому повідомленні — обидва місця. Старт наступного чату: прочитати копію з Project → звірити з репо (канон — репо) → видалити копію з Project. У Project живе лише самері останньої сесії.
