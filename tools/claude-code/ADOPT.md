# Адаптація наявного репо під каркас Claude Code — процедура

> живе доки: є репо Konst, не переведені на каркас (`tools/claude-code/ADOPTIONS.md` — хто вже). Змінилась процедура — правиться ЦЕЙ файл (подвійний аудит перед комітом).
> дім: `lens-governance:tools/claude-code/ADOPT.md` · каркас — `tools/claude-code/REPO_FRAME.md` · шаблони — `tools/claude-code/templates/`
> народилась: AE-Simulator S88, 02.10.2026 (перший переїзд Project → Claude Code, зроблений цією процедурою)

## Як запустити (Konst вставляє першим повідомленням у сесію репо)

```text
Адаптуй цей репо під каркас Claude Code за процедурою Konst-Andre/lens-governance, tools/claude-code/ADOPT.md (прочитай цілком). Етапи по черзі; до етапу 4 нічого не змінюй.
```

Сесії потрібні **два репо**: цей продукт і `lens-governance` (етап 7 пише рядок у журнал ядра). Ядра в сесії нема — читати цей файл через raw.githubusercontent.com, а рядок журналу на етапі 7 віддати Konst текстом для governance-сесії. Більше нічого вставляти не треба — усе нижче.

## Три шляхи — визначити на етапі 1

| шлях | ознака | що робимо |
|---|---|---|
| **А · звірка** | репо вже ведеться в Claude Code (є `CLAUDE.md`, самері в репо) — напр. AirLens | доповнити те, чого бракує; працююче **не перебудовувати** заради шаблону |
| **Б · переїзд** | репо будувалось під claude.ai Project (дзеркала Project, маніфести md5, самері в Project, сайт у корені) — напр. QR-Lens, EquipLens | повна процедура — етапи 0–7 нижче: розвідка → план → переїзд на гілці → злиття |
| **В · міст** | Konst свідомо лишає роботу в claude.ai Project — напр. Routes | лише короткий `CLAUDE.md`-покажчик (що це, де самері й черга, «основна робота — у Project»); каркас не нав'язувати |

**Продукти сімейства Lens** — розкладка Р-7 (рішення ядра G-W 24.09.2026; поки записане в тимчасовому журналі
`sessions/Lens_gov/Lens_MIGRATION_GW_ledger.md`, перенос у `kernel/Lens_REPO_LAYOUT.md` §4 — governance): `docs/` — **лише** опублікований
сайт · `lens/` — канон (черга, LOCK-и, реєстри, індекс продукту) · `sessions/` — живі самері · `archive/` — витіснене · `tools/` — стенди,
смоуки, скрипти · `sources/` — вихідні дані · README у корені й у кожній теці. Каркас **не ламає** Р-7 — ролі ті самі, теки інші:

| роль (каркас) | не-Lens (AE, AirLens) | продукт Lens (Р-7) |
|---|---|---|
| сайт | `site/` або інша тека виводу | `docs/` |

## Етапи

**0 · Знімок «до» (лише читання).** Числа, з якими порівнюватимемо: HEAD · гейти репо (вивід цілком у файл) · живий прод (головна
сторінка md5, ключові адреси даних і воркерів — HTTP-код **і вміст**) · що публікує хостинг (тека виводу, чи видно службове).
Без знімка «до» неможливо довести «нічого не зламав».

**1 · Розвідка (лише читання).** Прочитати `CLAUDE.md`/README, самері, чергу, маніфести; для кожної теки — **хто її читає**
(сайт, воркер, CI, редактор, люди) і за яким шляхом — греп по всьому репо і коду воркерів, перш ніж назвати щось «не потрібним».
Звірити живий прод із репо (Cloudflare: воркери, Pages-проєкти, тека виводу; GitHub: Pages, видимість репо). Визначити шлях А/Б/В.

**2 · Питання Konst** — коротким списком, лише те, чого не видно з коду: хто користувачі, що живе в проді, що можна ламати, що ні,
чи лишається Project. Чекати відповідей.

**3 · Діагноз і план** — текстом, без змін у файлах: що зайве, що дублюється, що лежить не там; цільове дерево з «чому» для кожної
теки (каркас §3 і таблиця вище); що **не чіпаємо** (шляхи, від яких залежать сайт, воркери, CI, редактори); план малими кроками
(кожен — один коміт із перевіркою); ризики й як їх помітити; практика ззовні з джерелом і датою. Мікроскоп і другий погляд — видимо.

**4 · Переїзд — на гілці `claude/…`, після «так».** `git mv` (історія зберігається), один предмет — один коміт, після кожного —
гейти «≡ до» і push з read-back. Порядок, що спрацював у AE: документи → інструменти → **тека публікації останньою** (найризиковіша:
міняє шляхи сайту, воркерів, CI одночасно) → `CLAUDE.md` · `REPO_LAYOUT` · `env_check` · `audit_prompts.sh` · хук → `DECISIONS` · `ARCHITECTURE` →
README і людські тексти. Прод (налаштування хостингу, злиття в `main` з автодеплоєм) — лише зі згоди Konst на цей крок.

**5 · Приймання** — див. нижче. **6 · Злиття** в `main` + перемикання хостингу (якщо тека публікації змінилась) + read-back проду.
**7 · Закриття:** самері (`templates/SUMMARY_template.md`) · рядок у `tools/claude-code/ADOPTIONS.md` ядра · стартове повідомлення в чат.

## Приймання — як перевірити, що все добре і нічого не зламано

| перевірка | як | ✓ коли |
|---|---|---|
| **прод не зламано** | ті самі проби, що в знімку «до» (етап 0): md5 головної, адреси даних, воркери | усе ≡ «до», крім того, що мало змінитись (і це названо) |
| **гейти ≡** | вивід гейтів до і після — `diff` | різниця лише очікувана; відомий червоний — той самий |
| **службове не публікується** | запит службового файла з живого сайту — судити за **вмістом** (Pages без `404.html` віддає головну з 200) | вмісту службового файла нема |
| **шляхи даних** | редактор / воркер / бот пише туди ж, куди репо (`env_check` рядок «прод») | ≡ |
| **чекліст** | `tools/claude-code/CLAUDE_CODE.md` | усе ☑ або свідомо «не потрібно» з причиною |
| **інструкції** | подвійний аудит `CLAUDE.md` (`audit_prompts.sh`) | знахідки обох моделей застосовано або названо |
| **пам'ять працює** — головний тест каркаса | **нова сесія** лише зі стартовим повідомленням; Konst питає три речі: «що відкрите?», «де живе X?», «як перевірити, що прод цілий?» | агент відповідає з репо (самері §0, `REPO_LAYOUT`, `env_check`), **не питаючи** Konst і не шукаючи в чаті |

Останній рядок — те, заради чого каркас: якщо нова сесія без чату знає стан проєкту, каркас працює. Якщо ні — що саме не знайшла,
те і є знахідка для каркаса (рядок у `ADOPTIONS.md`, правка `REPO_FRAME.md`).

## Чого не робити

- Перебудовувати працююче заради шаблону (шлях А). Шаблон — форма; зміст — від репо.
- Рухати теку публікації першим кроком або разом з іншим — лише окремим ходом, з детекторами й прев'ю гілки.
- Видаляти «непотрібне» без грепу по репо **і** воркерах (у AE «мертвий» `curatorCode` ще читали два смоуки).
- Переписувати історію git; переносити секрети в документи (лише імена).
- Лишати факт «у чаті»: усе, що з'ясовано на етапах 1–2, — у файли репо тим самим ходом.
