# Каркас репо під Claude Code — як влаштувати, щоб агент працював і пам'ятав

> живе доки: Konst працює з Claude Code. Змінилась практика — правиться ЦЕЙ файл (подвійний аудит перед комітом); репо підтягують при наступному тригері.
> дім: `lens-governance:tools/claude-code/REPO_FRAME.md` · вхід — `tools/claude-code/CLAUDE_CODE.md` · шаблони — `tools/claude-code/templates/`
> народився: AE-Simulator S88, 02.10.2026 (переїзд репо з claude.ai Project у Claude Code); зразки в живих репо — `AirLens`, `AE-Simulator`

Цей файл — не правила роботи (вони в профілі Konst, `tools/claude-code/PROFILE.md`), а **будова**: які файли, де, навіщо і як агент
ними користується. Читається цілком, коли заводиш нове репо або переводиш наявне; далі — точково.

---

## 1. П'ять принципів

1. **Контекст — головний ресурс.** Усе, що агент читає, займає вікно, а якість падає, коли воно заповнюється. Тому: коротка
   інструкція на старті, решта — точково за посиланням; старі речі — в архів, не в робочі файли.
2. **Пам'ять — лише репо.** Хмарний контейнер одноразовий, автопам'яті там нема, чат наступна сесія не бачить. Що не записано в
   репо — того не існує. Кожен факт, правило, домовленість — у файл того ж ходу.
3. **Один факт — один дім.** Дві копії розходяться (у AE «репо публічне» прожило в чотирьох файлах після того, як стало неправдою).
   Інші місця посилаються, не повторюють.
4. **Код старший за документ.** Розбіжність — назвати й виправити документ, а не повірити йому (AE S88: документація описувала
   «двері через `curatorCode`», а код уже давно перевіряв код у воркері).
5. **Перевірка, а не «схоже, що готово».** У кожного репо є команди з чітким ✓/✗, які агент запускає сам; висновок — з виводом
   команди, не з пам'яті.

## 2. Як агент пам'ятає (що завантажується і коли)

| що | коли потрапляє в контекст | наслідок |
|---|---|---|
| профіль Konst (налаштування акаунта) | кожна сесія, сам | загальні правила роботи; про конкретне репо — нічого |
| `CLAUDE.md` у корені | старт сесії, сам | правила цього репо; правка посеред сесії діє лише з наступної сесії (або `/clear`, `/compact`) |
| усе інше в репо | лише коли агент сам відкрив | тому `CLAUDE.md` мусить сказати, **що** відкрити на старті і в якому порядку |
| чат попередньої сесії | ніколи | передача — лише через самері в репо + стартове повідомлення |
| claude.ai Project (документи, поле Instructions) | ніколи в Claude Code | файл «лише в Project» = файлу нема |
| `claude -p` / субагент | свій окремий контекст, без профілю | модель указувати явно; профіль туди не доходить |
| `@шлях` у `CLAUDE.md` (без бектиків) | старт сесії, файл **цілком**, до 4 рівнів вкладення | лише для того, що потрібне щосесії; вказівник на файл — у бектиках (`` `шлях` ``): назва, не імпорт (code.claude.com/docs/en/memory, 04.10.2026) |

Модель сесії й заповнення контексту — заміряні: `get_session` (сервер `claude-code-remote`, без `session_id`) →
`session_context.model` · `effort_level` · `external_metadata.context_usage`.

## 3. Розкладка тек

```
<репо>/
├─ CLAUDE.md          інструкція агента (≤ ~200 рядків): що це · мова · старт · гілка · цикл · де що живе · гейти · секрети · самері
├─ README.md          обличчя для людини: що це, адреса, карта тек, як перевірити
├─ .claude/           settings.json + hooks/session-start.sh — інструменти гейтів ставляться самі
├─ <тека сайту>/      ЛИШЕ те, що публікується (Pages: тека виводу). Нічого службового — інакше воно стає сторінкою сайту
├─ worker/ · src/     код, що деплоїться не як статика
├─ docs/              документація для агента й людини (НЕ публікується)
│  ├─ REPO_LAYOUT.md  карта: порядок читання · дерево з ролями · хто що читає · карта переїздів
│  ├─ CHERGA.md       черга: відкрите зверху, порядок за ціною; стеля — 12 відкритих пунктів і вік 30 днів (`kernel/Lens_INDEX.md` §5), читається цілком
│  ├─ DECISIONS.md    рішення (вироки): нові зверху; чому так і що НЕ беремо
│  ├─ ARCHITECTURE.md як влаштовано: компоненти · шлях даних · деплой · секрети (лише імена) · відомі обмеження
│  ├─ AUDIT.md        журнал аудиту інструкцій
│  ├─ spec/ design/ brand/ …   довідники, джерела макетів, вихідні документи
│  └─ summary/        самері: <Продукт>_SUMMARY_<дата>[_sN].md
├─ tools/             env_check.sh · audit_prompts.sh · гейти · смоуки · детектори · генератори (НЕ публікується)
└─ archive/           витіснене: старі самері, білди, стенди. Не правиться, на старті не читається
```

**Тека сайту — головне архітектурне рішення.** Хостинг публікує теку, а не «потрібні файли». Корінь як тека публікації =
черга, самері, брендбук, ключі в коментарях стають доступні за адресою (AE до S88: `pages.dev/project/summary/…` → 200).
Cloudflare Pages: тека виводу — будь-яка (`site/`, `public/`). GitHub Pages з гілки — лише `/` або `/docs`; тоді `docs/` — сайт,
а документація — в іншій теці (`lens/`, як у сімействі Lens, Р-7). Воркер без статики (AirLens) — `docs/` вільна.
Перевірка «службове не публікується» — не за HTTP-кодом (Pages без `404.html` віддає головну з кодом 200), а за **вмістом**.

## 4. Документи і їхні ролі

| файл | питання, на яке відповідає | правило |
|---|---|---|
| `CLAUDE.md` | як тут працювати | лише те, чого агент не виведе з коду; «тут інакше» відносно профілю; подробиці — посиланням |
| `docs/REPO_LAYOUT.md` | що де лежить | структура змінилась → правка тим самим комітом |
| `docs/CHERGA.md` | що робимо далі | відкрите й порядок; зроблене — геть (історія в git і самері) |
| `docs/DECISIONS.md` | чому так | номер · суть · чому · практика (беремо / не беремо) · сесія і дата; старе не редагується, витіснене закреслюється |
| `docs/ARCHITECTURE.md` | як влаштовано | звіряється з кодом і живим продом; дата звірки в шапці |
| `docs/summary/…` | що сталося в сесії | §0 «ВІДКРИТЕ» зверху · що зроблено (коміти) · правила сесії повним текстом · контрольні суми · рецепт · стартове повідомлення |
| `docs/AUDIT.md` | коли й що аудитували | тригери · як · журнал; `env_check` нагадує через 30 днів |
| `tools/env_check.sh` | чи все гаразд на старті | рядки: база (HEAD, main попереду) · env (хости, змінні так/ні, гейти) · прод (живе ≡ репо) · `cloudflare:` + `⚠` (бюджет спільного акаунта, `tools/cloudflare/`) |

**Шапка кожного нового файлу:** `живе доки: …` (подія, після якої файл не потрібен) і дім, якщо не очевидний. JSON і згенероване — без.

## 5. Куди записувати знахідку

| що знайшли | дім |
|---|---|
| правило роботи в цьому репо | `CLAUDE.md` |
| рішення «робимо так, бо…» | `docs/DECISIONS.md` (новий номер) |
| будова, шлях даних, секрет (ім'я), обмеження | `docs/ARCHITECTURE.md` |
| задача на потім | `docs/CHERGA.md` |
| нова тека, переїзд | `docs/REPO_LAYOUT.md` |
| правило, що народилось у сесії | самері §2 повним текстом + дім вище в тому ж ході |
| патерн для всіх репо Konst | `lens-governance` — дім за таблицею «Знахідка з іншого репо → сюди» в `CLAUDE.md` ядра |

Запис без названого дому = не записаний. «Запишу пізніше» = загублено.

## 6. Життєвий цикл сесії

1. **Старт.** Хук ставить інструменти → `bash tools/env_check.sh` → `docs/REPO_LAYOUT.md` → найновіше самері (§0) → `docs/CHERGA.md`
   цілком → точково `DECISIONS` / `ARCHITECTURE`. Інша база, ніж у самері, — розібратись до роботи.
2. **Хід.** Цикл профілю (`tools/claude-code/PROFILE.md`, ЦИКЛ — тригери другого погляду лише там): план → мікроскоп → другий погляд
   → підказка effort → «так» Konst → код → гейти (і з підкинутою помилкою) → коміт → push → read-back (`git ls-remote` ≡ локальний HEAD).
3. **Велика перебудова** — на гілці `claude/…`, перегляд Konst, потім злиття; прев'ю гілки (Cloudflare Pages робить сам) або sandbox.
4. **Закриття.** Самері → коміт → стартове повідомлення в чат цілком. Пороги переїзду за контекстом — у профілі (`tools/claude-code/PROFILE.md`, ЗВІТ).

## 7. Перевірки — щоб «готово» було доведене

- **Гейти репо** — команди з ✓/✗ у `CLAUDE.md` з очікуваними числами (`✓19 ⚠1 ✗0`). Відомий червоний — сигнал «той самий
  червоний, що до ходу» (порівняння `diff` виводу до і після), не «зелений/червоний».
- **Зуби:** кожен гейт має режим підкинутої помилки (`--inject`) і червоніє на ньому — інакше зелений нічого не доводить.
- **Хук старту** (`.claude/hooks/session-start.sh`) ставить інструменти сам; змінив гейт — правиш хук тим самим комітом.
- **`env_check` звіряє прод:** живий код ≡ репо, тека публікації, службове не видно, давність аудиту.
- **Детектори UI** (Playwright) — для екранів; браузер контейнера не довіряє сертифікату проксі — живий сайт перевіряти `curl`.

## 8. Прод і секрети

- Прод (деплой, налаштування хостингу, `main` з автодеплоєм) — лише з явної згоди Konst на конкретний крок. Класифікатор безпеки
  середовища сам зупиняє такі дії — це запобіжник: зупинитись, спитати, не обходити.
- Секрети — ніколи в репо, коді, логах, самері, прев'ю; в документах — лише імена. Приватне репо — не виняток.
- Публічне (сайт, sandbox) — без секретів; чи можна туди реальні дані — рішення власника, записане в `docs/DECISIONS.md` репо.
- **Cloudflare — спільний акаунт.** Ліміти (запити на добу, збірки Pages на місяць) ділять усі проєкти; сесія одного репо не бачить
  інших. Тому: правила й бюджет — `tools/cloudflare/CLOUDFLARE.md` ядра, замір — `cf_budget.sh` рядком в `env_check` кожного репо;
  файл сам себе актуалізує (§5 там: >30 днів чи розбіжність з реальністю → звірка з джерелами окремим ходом).

## 9. Анти-приклади (AE-Simulator, до S88)

| що було | чому погано | як стало |
|---|---|---|
| тека `project/` — «дзеркало Project» з md5-маніфестом | дві правди; роль маніфесту бере git | розформовано: `docs/` · `tools/` · `archive/` |
| корінь репо = тека публікації | черга, самері, брендбук, каталог з бонусами — публічні сторінки | `site/` — тека виводу |
| `docs/` = брендбук | назва зайнята не тим; агент не знав, де документація | `docs/` = документація, брендбук → `docs/brand/` |
| документ «двері через `curatorCode`» | код давно інакший; агент і люди вірили документу | код старший; знайшов подвійний аудит |
| «агент не бачить контексту» | хибне твердження потрапило в правила | `get_session` → заміряно |
| аудит без `--model` | непомітно пішов на Sonnet (замовчування CLI) | модель — завжди явно й наперед у чаті |

## 10. Як адаптувати під своє репо

Беремо цілком: принципи (§1), пам'ять (§2), документи й ролі (§4), куди записувати (§5), цикл (§6), перевірки (§7), прод (§8).

в самері; що перевіряє `env_check` у проді. Порядок переводу наявного репо — `tools/claude-code/ADOPT.md`.
