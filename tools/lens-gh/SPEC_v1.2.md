## §0 Навіщо

Чат має дві руки, і вони не зʼєднані:
- **модель** кличе інструменти конектора, але все, що вони повертають, іде в контекст;
- **контейнер** (диск + терміналка) тримає лінт, валідатор, xlsx, але ключа до GitHub не має.

Наслідки v1.1, перевірені 26.09: `gh_read` віддає xlsx сміттям; xlsx 183 КБ = 244 644 символи base64 в одному виклику — за межею виводу; повна копія репо для лінту є лише через `git clone` з токеном у тексті інструкції. Ціль v1.2: **великі й бінарні файли ходять контейнер ↔ воркер ↔ GitHub, повз контекст; токена в чаті немає.**

Контейнер бачить воркер напряму (перевірено: `GET /` → `lens-gh 1.1.0`, `POST` доходить). Cloudflare API з контейнера теж досяжний.

## §1 Інвентар потреб → інструмент

| # | Потреба в роботі | v1.1 | v1.2 |
|---|---|---|---|
| 1 | повна копія репо в контейнер (лінт, валідатор, греп) | ✗ (лише токен у чаті) | квиток `tar` |
| 2 | один файл будь-якого типу в контейнер (xlsx з репо) | ✗ бінарні | квиток `get` |
| 3 | файл з контейнера в коміт (xlsx, великий .md) | лише через контекст | квиток `put` → `gh_commit {path, blob}` |
| 4 | read-back після коміту | `gh_read` → sha | + sha з `put` ≡ `git hash-object` |
| 5 | розмір у `dry_run` | ✗ `floor(len·3/4)`, +1 байт на паддінгу (рядок 397) | точний: з blob або з base64 без `=` |
| 6 | дрібні текстові правки | `edits` | без змін |
| 7 | розкласти файли з репо A в репо B (будь-який тип, ~200 КБ кожен) | текст — через контекст двічі; бінарні ✗ | `get`/`tar` з A → контейнер → `put` в B → `gh_commit {blob}`; контекст — лише sha |

## §2 Новий інструмент `gh_ticket`

Вхід: `repo`, `op` ∈ {`tar`, `get`, `put`}, `ref` (для `tar`/`get`, типово — гілка за замовчуванням), `path` (для `get`), `note` — коротке «навіщо» (≤ 80 символів, без даних і секретів).
Квиток `put` діє на всі завантаження в межах TTL: пачка файлів = один квиток.
Вихід: URL + готовий рядок `curl` для контейнера + час смерті.

Квиток = `base64url(payload).HMAC-SHA256(payload, TICKET_KEY)`; payload = `{repo, op, ref, path, note, exp}`; `exp` = зараз + 10 хв.
`TICKET_KEY` — новий секрет воркера (≥32 символи), окремий від `MCP_KEY`: витік квитка не дає доступу до MCP.

## §3 Маршрути воркера

| Маршрут | Що робить | CPU |
|---|---|---|
| `GET /t/<квиток>` (`tar`) | `GET /repos/{repo}/tarball/{ref}` з `GH_TOKEN` → віддає `response.body` потоком | ~0: мережа не рахується |
| `GET /t/<квиток>` (`get`) | `GET /repos/{repo}/contents/{path}?ref=` з `Accept: application/vnd.github.raw` → потоком | ~0 |
| `POST /t/<квиток>` (`put`) | тіло **вже** `{"content":"<base64>","encoding":"base64"}` від контейнера → пересилається в `POST /repos/{repo}/git/blobs` **без розбору** → `{sha, size}` | ~0 |

Перевірка квитка — одна спільна функція для всіх маршрутів (підпис, `exp`, `op` відповідає методу, `repo` під `OWNER`). Будь-яка помилка → 404 без пояснень.
Кожне використання квитка — один рядок `console.log`: час · `op` · `repo` · `path` · розмір · `note`. Слід видно в Cloudflare → Workers → `lens-gh` → Logs (потрібне ввімкнене Workers Logs; перевірити при деплої).

## §4 `gh_commit` — новий режим зміни `blob`

`{path, blob: "<sha>"}` — файл, уже завантажений квитком `put`. Воркер перевіряє `GET /git/blobs/{sha}` (існує, розмір) і ставить sha в дерево. `dry_run` показує `path · sha · size`. Рівно одне з: `edits` / `content` / `content_base64` / `blob` / `from` / `delete`.

## §5 Межі (Cloudflare Workers Free, документація 27.09.2026)

CPU 10 мс на запит (мережа не рахується) · тіло запиту ≤ 100 МБ · 50 зовнішніх підзапитів, редирект рахується окремо (`tarball` → `codeload` = 2) · памʼять 128 МБ.
Звідси правило: **воркер нічого не кодує й не розпаковує** — лише перевіряє підпис і пересилає потік. base64 робить контейнер.

## §6 Безпека

- Квиток світиться в чаті: живе 10 хв, одна операція, один репо. Сам `GH_TOKEN` з воркера не виходить.
- `put` без коміту лишає «висячий» blob у GitHub — невидимий, прибирається GC. Коміт — лише через MCP з `expected_head` і «так».
- Одноразовість квитка (KV) у v1.2 **не робимо**: TTL + вузька дія достатні; перегляд — якщо зʼявиться причина.
- Репо приватні: квиток `tar`/`get` = доступ на читання на 10 хв. Не публікувати в документах, самері, репо.

## §9 Рецепти для `CHAT_TOOLS.md` — лише після деплою, лише зі смоуку

Рецепт = готовий рядок для контейнера (клон · один файл · пачка в інший репо). Він потрібен, бо кожна задача має пастку, на якій новий чат спіткнеться сам:
- `curl` без `--fail` на 404 мовчки збереже сторінку помилки під іменем `.xlsx` → рецепт: `curl --fail -sS … -o файл` + `git hash-object` проти sha з `gh_read`/`put`;
- tarball GitHub кладе все в теку `Konst-Andre-<репо>-<sha>/` → рецепт: `tar xz --strip-components=1`;
- base64 з переносами рядків ламає JSON для `put` → рецепт: `base64 -w0`.

Антиприклад, якого уникаємо: рецепт, написаний окремо від коду, розходиться з воркером при першій правці — і бреше впевнено. Тому **рецепти не пишуться руками**: смоук §7 оформлюється скриптом `tools/lens-gh/smoke.sh`, а `CHAT_TOOLS.md` цитує з нього рядки дослівно. Змінився маршрут → смоук червоний, доки рецепт не виправлено; правка `worker.js`, смоуку й `CHAT_TOOLS.md` — один коміт. До деплою рецептів у `CHAT_TOOLS.md` немає: рецепт для неіснуючого інструмента — брехня.

Після v1.2 чекає чат Routes: xlsx жовтня (`months/2026-10/route_amended.xlsx`) + К1; транспорт — документ Project Routes `ROUTES_PENDING_2026-10.md`.
