репо ім'я без репо двозначне.

серед імен і дає хибний ✗. Якість упала б мовчки — рівно те, чого мета забороняє.

**Детектор (К2) — окремий хід коду; правило набуває сили з цього ходу.**

## §2 Ф2 · Живе самері governance — у репо, тека `sessions/Lens_gov/`

**Тригер.** Governance-сесія видає самері.

**Дія.** Самері пушиться в `lens-governance`, тека `sessions/Lens_gov/`, тим самим ходом, що й закриття сесії. У Project **не кладеться**. `Lens_INDEX` §5 оголошує його **іменем** (Ф1 ще без детектора, §1-б) і називає теку. Витіснене (стеля 2, `wsd 1.8`) переїжджає `sessions/Lens_gov/` → `archive/summaries/Lens_gov/` — як досі з Project. Гейт `--live` дивиться на `sessions/Lens_gov/`. Скрипти кроків сесії — одразу в `archive/summaries/Lens_gov/` тим же пушем.

**Чому.** G-T пообіцяла Konst «востаннє за старою схемою», а G-U повторила стару інструкцію «поклади в Project» — обіцянка без механізму (слово Konst, 24.09.2026). Живе самері — єдина причина, через яку governance ще вантажила Project.

**Межа.** Лише governance. Самері продуктів — **Ф2-б**, вирішується разом із Ф3 (де в продуктовому репо живе не-деплой). `sessions/` ≠ `archive/`: живе ⟂ доказ — межу Ф4 не зачеплено.

**Практика ззовні (мікроскоп G-U, 24.09.2026).**
- `Routes:REPO_LAYOUT.md` — `sessions/` = «вмирає з подією, лишається слідом»; і живе, і минуле самері в одній теці. Беремо теку для живого. НЕ беремо злиття з архівом — у Lens `archive/` = корпус гейтів (Ф4 ще не вирішено).
- ADR (Nygard; adr.github.io; github.com/opendatahub-io/architecture-decision-records, перевірено 24.09.2026) — рішення живуть markdown-файлами в репо поруч із кодом, витіснене лишається з позначкою. Беремо «в репо, не деінде». НЕ беремо нумерацію `0001-…` — у Lens координата в імені вже є (`G<літера>_<тема>`).

## §3 Ф4 · Корпус гейтів — `archive/` лишається в ядрі; гейт мережі не має

> ⚠ **Переглянуто G-W 24.09.2026 (§4).** П.1 і п.4 (архів продуктів у ядрі), детектор (2) і «Наслідок для Ф3» — **історія**, не діють. П.2–3 (гейт без мережі · `--repo` · ⓘ без кореня) — **чинні**.

**Тригер.** Рішення, куди переїжджає файл продукту (Ф3 · Ф2-б), або правка гейта, що читає `archive/` (`G12` · `G19` · `G22`) чи чужий репо (`G8` після детектора Ф1).

**Дія.**
1. **`archive/` усіх продуктів лишається в `lens-governance`.** У продуктовий репо може їхати лише **живе** (`sessions/`, канон — за Ф3). Формула: **`sessions/` — у продукті, `archive/` — у ядрі.**
2. **Гейт не ходить у мережу.** Жоден гейт `Lens_validate.py` не робить HTTP-запиту. Чужий репо гейт бачить лише як **локальний сусідній корінь**, переданий аргументом (`--repo ІМ'Я=тека`); збирання коренів (clone · codeload) — окремий крок сесії **до** гейта.
3. **Корінь не дано → ⓘ «не перевірено», не ✗.** Відсутній корінь — неповний замір, а не дефект канону.
4. Витіснене самері продукту (якщо Ф2-б покладе живі в продуктовий репо) переїжджає в `lens-governance:archive/summaries/<Продукт>/` — перенос між двома репо, два коміти; допустимо як один хід архівації.

**Чому.** Корпус `G19` — доказ **правил родини**: правила `wsd` спрацьовують переважно в продуктових сесіях. Розрізаний по репо, він дає масовий хибний ✗ «правило жодного разу не спрацювало» щойно одного кореня немає (інвентар GT §2: ~128 → ~114 самері). Корпус наскрізний — отже, живе в одному центральному репо. Мережа в гейті зламала б принцип, записаний у коді `G12` (`Lens_validate.py` р.425: гейт, що вимагає мережі, не запуститься саме тоді, коли потрібен), дала б 403 rate-limit (`Lens_INDEX` §8, рівень 1) і вимагала б токена в гейті для приватного `QR-Lens`.

**Анти-приклад.** Перенести `archive/summaries/EquipLens/` у репо `EquipLens` до рішення, звідки `G19` бере корпус: 31 самері зникає з підрахунку, правила EquipLens-сесій читаються мертвими, `К3-1` пропонує їх виселити. Гейт «зелений» по формі й хибний по суті.

**Детектор (К2).** (1) `grep -nE 'urllib|requests|http\.client|socket' kernel/Lens_validate.py` = 0 — інакше ✗ «гейт із мережею». (2) `git ls-files archive/` у продуктових репо = 0 — інакше ✗ «архів розрізано». Обидва механічні; вбудувати в `--gov` — заявка разом із детектором Ф1 (`G24`-хід).

**Наслідок для Ф3 (названо, не вирішено).** Якщо архів продуктів у ядрі, то й `products/` може лишитися тут, а продуктові репо — чистим деплоєм Pages. Вирішує Ф3.

**Практика ззовні (мікроскоп G-V, 24.09.2026).**
- `actions/checkout` README, сценарій «Checkout multiple repos (side by side)» — кожен репо окремим кроком у свою теку, приватний — власним PAT (перевірено 24.09.2026). Беремо: збирання коренів — окремий крок, гейт читає лише диск. НЕ беремо: CI-оркестрацію — Actions у Lens немає.
- Центральний лог рішень: наскрізні рішення, розкидані по репо, важко відстежувати, їх тримають в окремому репо (Maruthi, Medium, 19.07.2021); для кількох репо достатньо markdown у репо, агрегатор — коли репо багато (Catio, 15.06.2026). Беремо: наскрізний корпус — в одному репо (ядро). НЕ беремо: агрегатор/сайт — ≤9 репо.
- Відкинуто: **Б** — гейт через API (мережа, rate-limit, токен); **В** — корпус розрізаний, гейт з кількома коренями `--corpus` (правка трьох гейтів, клон N репо щостарту, масовий хибний ✗ при відсутньому корені).

## §4 Ф3 + Ф2-б · Продуктовий репо самодостатній; ядро — лише мозок

> Ухвалено G-W 24.09.2026, слово Konst. **Переглядає Ф4 (§3):** архів продуктів іде в продукт, не лишається в ядрі.
> Стан переносу по продуктах — тимчасовий журнал `sessions/Lens_gov/Lens_MIGRATION_GW_ledger.md` (видаляється після переносу).

**Тригер.** Файл продукту шукає дім; нова сесія продукту; заводиться новий продукт; правка гейта, що читає продуктові файли.

**Дія.**
1. **`lens-governance` тримає тільки родинне:** `kernel/` (правила, протоколи, Cookbook, модулі, гейт-скрипти) · крос-Lens FINDINGS (`products/Lens_glass_FINDINGS.md`) · `archive/summaries/Lens_gov/` · `archive/Lens_iOS_cookbook.md` · `archive/superseded/canon_delta_A45_material_lever_manifest.md`.
2. **Продуктовий репо самодостатній:** код і білд · README · manifest · канон продукту (`*_MASTER_LOCK` · `*_valuesLOCK` · реєстри · `*_CHERGA`) · `sessions/` (живі самері, Ф2-б) · `archive/` (витіснені самері, стенди, матриці) · стенди · смоуки · скрипти й продуктові гейти.
3. **Залежність одностороння.** Продукт посилається на ядро (правило за номером). Ядро посилається на продукт лише як на **історію походження** — `Репо:шлях` (Ф1); правило ядра мусить працювати, не відкриваючи продуктового файлу. Старі посилання іменем не переписуються (§1 п.3).
4. **Гейти підлаштовуються під модель, не навпаки.** `G19` · `G22` · `G10` · `G8` читають продуктові репо з локальних коренів `--repo ІМ'Я=тека`, зібраних на старті сесії; кореня нема → ⓘ, не ✗; мережі в гейті немає (§3 п.2–3 чинні).
5. **Хостинг.** GitHub Pages — лише швидкий перегляд; бойовий хостинг — Cloudflare Pages; репо продукту може стати приватним будь-коли. Отже службове не мусить потрапляти в опубліковану теку — розкладка всередині продуктового репо вирішується на першому переносі (журнал, О-1).

**Чому.** Ядро — переносний мозок (як CLAUDE.md для агента): новий Project = шаблон інструкції + ядро + репо продукту. Змішане ядро тягне продуктовий шум у кожну сесію й кожен Project. Аргумент Ф4 «корпус `G19` розріжеться» — про зручність гейта, а гейти наші: переписати гейт дешевше, ніж підлаштувати під нього архітектуру (слово Konst, G-W).

**Анти-приклад.** G-W хід 0: Claude порадив лишити все продуктове в ядрі, бо «одному кореню гейта зручніше» — архітектура під власний скрипт, протилежна меті оператора.

**Детектор (К2).** Після переносу `git ls-files products/ archive/summaries/ archive/stands/ archive/matrices/ archive/superseded/` у `lens-governance` = рівно перелік п.1 — інакше ✗ «продуктове в ядрі». Заявка в `--gov` — разом із `G19 --repo` (журнал, хід 7).

**Практика ззовні (мікроскоп G-W, 24.09.2026).**
