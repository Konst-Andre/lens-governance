# Lens · NEWPROJECT — рецепт заведення нового Project

> **Задача, яку це вирішує.** Один Claude Project на один продукт — щоб робочий простір
> не був перемішаний (`QR` + `KPI` + `Фармастор` + `StockCheck` + `VTM` в одній теці).
> При цьому якість мислення й знання мають лишитись ті самі: новий Project має «знати» рівно
> те саме, що знає цей.
>
> **Що переноситься:** файли ядра (нижче). **Що НЕ переноситься:** пам'ять.

---

## §1 Головне обмеження — пам'ять не переносна `[07.2026]`

Кожен Claude Project має **власний ізольований** простір пам'яті. `conversation_search`
теж бачить тільки чати всередині поточного Project. Отже:

- накопичена пам'ять цього Project у новий **не приїде** і скопіювати її не можна;
- це **не втрата**, якщо профіль лежить у файлі — саме для цього існує `Lens_PROFILE.md`;
- побічний ефект **корисний**: пам'ять нового Project наповнюється фактами **одного** продукту,
  без перехресного забруднення сусідніми. Зараз навпаки — пам'ять змішана по п'яти продуктах.

*Тригер перевірки: якщо пам'ять колись стане наскрізною між Projects — `Lens_PROFILE.md`
однаково лишається канон-домом, бо memory неавторитетна (wsd 2.1).*

## §3 Головний ризик — розходження ядра, і як його знімати

**Ризик.** Ядро лежить у N Projects копіями. Правиш wsd у Project StockCheck — копії
в чотирьох інших Projects мовчки протухають. Через два місяці Claude у QR-проєкті працює
за протоколом двомісячної давнини й **не має способу про це дізнатись**.

**Рішення — одне джерело правди поза Projects.**

1. Ядро живе в **репозиторії** (у тебе вже є GitHub для Pages — заведи теку `governance/`
   або окремий репозиторій `lens-governance`).
2. Канон правиться **в репозиторії**, не в Project. Project — це завжди **копія**.
3. Кожен файл ядра несе у другому рядку штамп: `> KERNEL vN · ДД.ММ.РРРР`.
4. `Lens_INDEX.md` називає **поточну** версію ядра.

**Детектор (К2).** На старті сесії Claude читає `Lens_INDEX.md` першим (wsd 1.1) і бачить
штамп. Якщо штамп у будь-якому іншому файлі ядра **не збігається** з версією в індексі —
ядро розійшлось, і це видно **до** початку роботи, а не після зламаного патча.
Без штампа розсинхрон невидимий у принципі.

**Коли піднімати `vN`:** будь-яка зміна у wsd або Cookbook. Не «за розкладом» — за фактом правки.

## §4 Порядок заведення (8 кроків)

1. **Створити Project** з іменем продукту (`Lens · StockCheck`, `Lens · QR`, …).
2. **Залити ядро** (§2, пп.1–7) з репозиторію — не з іншого Project.
3. **Вставити інструкцію** (§5) у Project instructions, підставивши назву продукту.
4. **Залити продуктовий шар** — білд, локи, останні 2 самері.
5. **Перевірити штампи:** усі файли ядра — та сама `KERNEL vN`.
6. **Перше повідомлення в новому чаті** — стартер із §6.
7. **Не переносити старі самері.** Вони лишаються в локальному архіві поза project knowledge
   (wsd 1.8). Якщо колись знадобиться конкретний — заллєш точково.
8. **Старий змішаний Project** не видаляти одразу: тримати як архів, доки всі продукти
   не переїхали й не відпрацювали по одній сесії кожен.

НОВИЙ ФАЙЛ — обов'язково з рядком «живе доки: …» у шапці (wsd 1.8).

Усе інше — форма правил (К1/К2), маршрутизація записів (12.11), самері, віджети,
compare-раунди, device-арбітр, стиль пояснень — канонічно живе у wsd і Lens_PROFILE.md.
